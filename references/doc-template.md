# doc.md 模板

写入路径：`<specs_root>/{feature_name}/doc.md`

```markdown
# {需求名称} 设计文档

| 属性 | 内容 |
| --- | --- |
| 文档状态 | 待评审 / 已确认 |
| 目标版本 | {版本或迭代} |
| 文档用途 | 本次需求的方案事实源，冲突时以本文为准 |

## 背景和目标

{为什么做，解决谁的什么问题。目标写成可判定的结果，不写"提升体验"这类无法验收的话}

## 当前代码库现状

{相关模块、关键类、现有链路。写清楚哪些是既有能力，哪些缺失}

## 架构和技术设计

{整体方案。用 mermaid 画结构，不用 ASCII}

```mermaid
flowchart LR
    A[入口] --> B[处理]
    B --> C[产出]
```

## 数据流或调用链

{一次完整流程从触发到结束经过哪些环节，状态如何流转}

## 关键接口与数据结构

{只列关键签名、字段和配置示例，不贴完整实现}

## 错误处理、兼容性和边界情况

{失败时的行为、降级路径、老版本兼容、并发与生命周期边界}

## 测试策略

{测哪一层、在哪个接缝测、用什么命令跑、什么算通过}

## 工作项拆分

{工作项清单落在这里，编号用 W1、W2，格式见 split-format.md}

## 明确不做

{本次不覆盖的范围，以及不做的理由}
```

## 写作要求

1. 架构与数据流优先 mermaid
2. 不贴完整实现代码，只留关键签名、数据结构、配置示例
3. 不写无信息量的分割线和套话
4. 严格 YAGNI，用户没要求且设计不需要的能力不要加
5. 目标和验收口径必须可判定，禁止「优化体验」这类无法验证的表述
