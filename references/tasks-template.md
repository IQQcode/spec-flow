# tasks.md 模板

写入路径：`<specs_root>/{feature_name}/tasks.md`

## 头部

```markdown
# {需求名称} 实施计划

> 面向执行者：逐个 Task 实施本计划，步骤用 checkbox (`- [ ]`) 跟踪。

**目标：** {一句话描述这将构建什么}

**架构：** {2 到 3 句描述方案；无 doc.md 时基于拆分上下文简述}

**技术栈：** {关键技术与库}

**工作项清单来源：** {doc.md 工作项拆分章节，或本文件下方列表}

**提交绑定策略：** 提交信息前缀带上工作项编号，例如 `W2: 补齐离线降级路径`

## 工作项任务列表

| Task | 工作项编号 | 工作项标题 |
| --- | --- | --- |
| Task 1 | W1 | {标题} |
```

## 单个 Task 契约

```markdown
### Task N: {工作项标题}

## 目标
{此任务必须产出的可观察结果}

## 上下文
{此任务在整体方案中的位置，来自 doc.md 或拆分结论}

## 工作项绑定
- 编号：W1
- 来源：{doc.md 工作项拆分章节，或本计划头部列表}

## 范围
- 范围内：{可以改什么}
- 范围外：{相邻但本任务不得动的部分}

## 相关文件
- 可能修改：`exact/path/to/existing.kt`
- 可能创建：`exact/path/to/new_file.kt`
- 参考：`exact/path/to/reference.kt`

## 验收标准
- [ ] {可观察行为或交付物}
- [ ] {重要边界情况或失败行为}

## 测试预期
- 单元测试：{要覆盖的具体行为}
- 集成或运行时验证：{具体做法}
- 命令：`exact command to run`
- 预期结果：{什么算通过}

## 约束
- {必需的 API、兼容性、依赖、风格或架构约束}
```

## 转写规则

1. 一个工作项对应一个 Task，禁止一拆多或多合一
2. 工作项内部步骤写在 Task 描述里，不上升为主任务
3. 每个 Task 都要能被一个没有本次会话上下文的执行者独立读懂

## 自审红线

出现以下任一情况，计划视为不合格，必须改到合格再交给用户 review：

- `TBD`、`TODO`、`稍后实现`、`补充细节`、`implement later`
- 「加上合适的错误处理」但没说哪些错误重要
- 「写测试」但没有具体行为、命令和预期结果
- 「同 Task N」但没有重复必要上下文
- 引用了任何 Task 里都没定义的类型、函数或方法
- 相关文件写成目录或模糊路径，而不是具体文件
