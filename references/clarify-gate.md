# 不确定即停：判定清单与提问规范

这条规则横切全部六个阶段。目的是把「猜错了再返工」换成「先问清再动手」。

## 必须提问的信号

命中任意一条就停下提问，不要边猜边做：

1. **需求有多种合理解读**，且不同解读会导致不同的改动范围或不同的验收口径
2. **方案存在真实分歧**，两条路径各有明显代价，不是一眼可判的优劣
3. **改动会触及不可逆或外部可见的东西**：删文件、改数据结构、动线上配置、改鉴权、推送到远端
4. **关键事实无法从代码或文档中确认**，例如某行为是刻意设计还是历史遗留，某字段是否还有消费方
5. **用户的措辞与代码现状冲突**，按字面做会引入错误
6. **范围边界不清**：不确定某个相邻模块算范围内还是范围外
7. **验证方式未知**：不知道用什么命令、什么预期结果才算通过

## 可以自行决定的事

命中下列情况不要提问，选一个合理做法并在结果里说明即可，避免用问题淹没用户：

1. 命名、格式、注释密度、代码风格，跟随周边既有代码
2. 等价方案之间的取舍，且两者代价都很小
3. 能通过读代码、跑命令、查文档自行确认的事实。先去查，查不到才问
4. 用户已经明确拍板过的决定，不要重复确认

## 提问格式

有结构化提问工具时用它，一次最多三个问题。没有就用编号列表让用户回数字。

```text
标题：{一句话点出待决问题}

1. {选项标题}（推荐）：{推荐理由，以及选择后的影响}
2. {选项标题}：{选择后的影响或代价}
3. {选项标题}：{选择后的影响或代价}
```

要求：

1. 每个问题都要能改变后续动作。不影响判断的不要问
2. 互不依赖的问题合并成一次问，减少来回轮次
3. 每个选项都写清选择后的影响或代价，不要只给名字
4. 给出推荐项并说明理由，但不要替用户决定
5. 需要的是开放信息而不是选择时，直接问，不要硬凑选项

## 需要深挖时

方案本身还很模糊，或用户明确要求压力测试自己的想法时，本机装有 `grill-me` 或 `grilling` skill 的话可以调用它做一轮追问式访谈。这是可选增强，没有这些 skill 时按本文件的清单和格式提问，效果不受影响。

## 反例

以下行为视为违反本规则：

1. 用「我先按 A 方案做，不对再改」代替提问
2. 一次抛出七八个问题，其中多数不影响判断
3. 问了问题但没等回答就继续动手
4. 选项只有标题，没写清各自的代价
5. 明明能通过读代码确认的事，拿来问用户
