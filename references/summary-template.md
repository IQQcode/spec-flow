# summary.md 模板

写入路径：`<specs_root>/{feature_name}/summary.md`

收尾阶段写这份文件。它服务两类读者：下次接手同一模块的人，以及需要判断本次结论是否仍然成立的 Agent。

```markdown
# {需求名称} 总结

## 问题描述

{最初要解决什么，用户视角}

## 根因分析

{Bug 类需求写根因；功能类需求写为什么现有能力不够}

## 方案结论

{最终采用的方案，以及关键设计决策}

## 已完成内容

- {做了什么，一条一件事}

## 改动文件

- `path/to/file`，{改了什么}

## 验证结果

- [x] {已验证通过的项，附命令或证据}
- [ ] {未完成或未验证的项，写明原因}

## 后续建议

1. {下一步该做什么}
```

## 硬要求

1. 验证结果用 checkbox。没做到的保持未勾选并写明原因，禁止假装全绿
2. 「改动文件」列真实路径，写完后核对文件确实存在
3. 结论要写清适用边界，避免下次被当成普适真理误用
4. 项目里有 specs 索引文件时，同步更新索引
